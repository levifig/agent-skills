# Change Work Model — Role-Named Narrative, Task-File State, Shipped-Not-Shaped Release Gating

## Problem

The work unit today is one `change.md` serving three lives — the pitch (shaping deliverable), the plan (units and verification), and the machine surface (frontmatter carrying `lineage`, `predecessor`, `release-after`). Four failures follow:

1. **The release gate cannot distinguish shaped from shipped.** The gate's satisfaction test for an arc terminal is node presence in HEAD plus structural executability — precisely what shaping produces. Proven 2026-07-25 in an isolated worktree: merging the sole shaping commit of terminal `spec-conversion-and-guidance-sweep` plus one missing frontmatter line takes `loaf release --dry-run --bump minor` from blocked to a complete stable 2.1.0 plan with zero lines of the conversion sweep implemented. Shape-first makes that collision the expected order of events, not an abuse.
2. **Shaping edits and execution edits are indistinguishable in history.** Every commit that modifies `change.md` looks the same, whether it refines scope or records delivered work, so any git-provenance rule keyed on the single file inherits the ambiguity.
3. **The document conflates roles the corpus keeps separate.** Observable outcomes and boundaries (the spec sense), the technical route (the plan sense), and the original unshaped ask (the brief sense) all share one file, so agents and humans cannot be pointed at "the contract" or "the approach" without reading everything.
4. **Nothing in the structure supports tracker parity or stable reference.** The unit maps naturally to a parent issue with sub-issues in Linear or GitHub, but prose sections give a sync adapter no stable task identity to target, and the retired `SPEC-XXX` counter cannot return — a global sequence needs a mint authority, and a branch-native, offline-capable, multi-worktree model deliberately has none.

Beneath these sits a work-model ambiguity this unit resolves: `journal-reliability-foundation` executed as one mega-unit across 20+ PRs because discovered problems were absorbed as units instead of spun out as Intents, and because nothing in the vocabulary carried the integration discipline.

## Hypothesis

Keeping **Change** as the bucket and splitting **narrative from state** — role-named narrative documents (`brief.md` optional kickstart, `shape.md` required contract, `plan.md`/`design.md` accretive technical route) that settle at shaping, plus `change.json` (machine metadata) and `tasks/TASK-NNN-slug.md` (identified task files whose subtask checkboxes are checked in the commits that deliver the work) — makes execution evidence machine-derivable along the true boundary: prose is shaped, state is executed. The release gate then hangs on the release itself: a change optionally declares the `target_release` it is bound for, and cutting that version stable requires its whole cohort *executed and verified* rather than merely materialized, closing the proven defect; slug-plus-local-number identity gives reference and tracker sync a coordination-free scheme; and each document name matches its reserved meaning in the agentic corpus, so "read the contract" and "update the approach" resolve unambiguously.

## Scope

**In**

- Change folder anatomy at the existing root: `docs/changes/YYYYMMDD-slug/` containing `change.json`, `shape.md` (required), `brief.md`/`plan.md`/`design.md` (optional, accretive), `tasks/TASK-NNN-slug.md`, and two change-scoped artifact directories — `research/` (inputs to shaping: spikes, reaction artifacts, evidence that Decisions cite) and `reports/` (authored outputs, mostly HTML, named `YYYYMMDD-HHMMSS-<kind>-<slug>.html` — a closed kind registry ships in the binary: ceremony kinds `approval` and `review` are reserved and machine-findable; informational kinds `visual`, `audit`, and `note` round it out, with `note` as the deliberate escape hatch; extending the registry is a normal change to Loaf — agent-to-human communication). Everything a change generates lives inside its folder.
- `change.json` schema: identity (`change`, `created`, `branch`) plus an optional **`target_release`** — the release this change is bound for, in one canonical literal form: `MAJOR.MINOR.PATCH`, no `v` prefix, no leading zeros, no prerelease or build suffix (prereleases never gate). The cohort (all changes sharing a target) *is* the arc: derived, never declared as a graph. Declaring a target opts the change into the strong gate; the field is mutable by design — roadmaps slip, and a retarget (including removal, dropping the obligation) is a visible, reviewable diff, surfaced from history and at release preflight, never blocked. No arc fields, no chains, no frozen designations.
- `shape.md` carries the contract: problem, boundaries, scope, decisions, and the verification criteria. Executable criteria declare their command and expected result; prose criteria are the human-review tier. It is the change's body under tracker sync — project description or tracking issue, per the mapping mode — and the digest surface for receipts.
- `brief.md` semantics: the optional archeological kickstart — written when capture precedes shaping (a promoted spark, idea, or Intent; a pasted bug report), superseded by `shape.md`, never updated after, and never mechanically load-bearing. A brief-only folder is legal and non-executable: derived state "captured, not shaped".
- Task files: `TASK-NNN-slug.md` numbered-record identity inside the owning `tasks/` directory — identity under the artifact-names guard's designed exemption (`task-`-prefixed records in a `tasks/` dirBase); the slug portion must never cite other work units. Frontmatter relations use the tracker-native closed set — `parent` (containment: single-valued, children derived, arbitrary depth), `blocks`/`blocked-by` (sequencing: inverses derived from either direction), and `relates-to` (association). `parent` carries no completion or provenance semantics — completion stays per-file checkbox state, and a parent that must wait on its children declares `blocked-by` explicitly. Relation targets are `TASK-NNN` within the owning change — cross-change relations are forbidden (between changes, cohort membership and git order carry the sequencing); unknown relation keys are violations (closed frontmatter schema), and duplicate or contradictory declarations normalize idempotently or fail check. The body is a self-sufficient delegation packet: objective, scope boundaries (what the task must not touch), context pointers into `shape.md` and `research/`, how to acquire what's needed, checkbox steps, and task-level verification instructions — complete enough to hand to a subagent as its entire brief. Completion is derived from checkbox state — never stored. Checkboxes stay unlabeled; `TASK-NNN.A` letter labels are permitted prose convention, never parsed or validated.
- Layout coexistence in place: the loader detects the new layout by `change.json` presence and falls back to legacy single-file `change.md` in the same root — no root migration, both layouts first-class until a named removal boundary.
- `loaf change init` scaffolds the new layout; `loaf change check` validates both; `loaf change tasks --json` projects a stable-ID task index on demand; `loaf change show` derives the change's PR set from squash subjects (`(#N)`) of commits touching its folder; `loaf change report new <slug>` stamps a report's minimal shell (charset, provenance header, token skeleton, timestamp-and-kind name in `reports/`) and prints the design language to stdout — invariants as side effect, guidance as just-in-time context, layout the author's. `loaf change list` is redefined as the units projection (layout, target, derived state; `--target` filters a cohort) — its lineage-specific contract retires with the graph.
- Execution provenance: a change counts as executed when at least one commit in HEAD ancestry modifies its `tasks/` files and also modifies at least one path outside `docs/changes/` entirely — so cross-change task edits never count; the gate path (changes declaring a `target_release`) tightens this to commits whose diff flips a checkbox `- [ ]`→`- [x]` outside code fences (reverse flips, added unchecked boxes, and whitespace edits are non-events). The path grade feeds derived display states for every change; the flip grade is what gates. Old-layout fallback for non-gating states: keyed on `change.md`. Provenance is the coarse filter — the receipt is the lock.
- Release gate rewrite: the preflight computes the **candidate version first** (restructuring today's preflight-before-planning order) and gates when the candidate is stable: cutting `X.Y.Z` requires **every change with `target_release: X.Y.Z` to be materialized, structurally valid, executed at the flip grade, and receipt-verified** — one shaped-only cohort member blocks the whole version; changes without a target never gate anything. Target matching is byte-equality between the canonical target literal and the computed stable candidate. A prerelease *candidate* bypasses (that is what `--bump prerelease` produces); **finalizing a prerelease into stable — including `--post-merge` — gates the stable target's cohort**, closing today's post-merge bypass. Lower-versioned incomplete cohorts warn, never block (their own cut is where they block). Retarget and target-removal events relevant to the candidate are surfaced in the preflight output.
- Terminal verification receipt: `loaf change verify` runs the declared executable criteria and writes a committed receipt recording the criteria digest **and the verified commit** — a cache of verification, not a credential. Approach churn in `plan.md` never expires a receipt; criteria changes always do. Freshness tolerates the receipt's own commit: preflight re-runs criteria only when some later commit touches a path other than the receipt file itself. H-tier criteria are review material, never gate input. Receipts are new-layout-only — a legacy cohort member must first convert via the sanctioned atomic replace, because digesting prose does not make it executable. Required only for changes declaring a `target_release`: declaring a target is opting into verification; ordinary changes carry zero ceremony.
- Identity and reference scheme: the slug is the identity (global uniqueness already enforced), `slug/NNN` references a task, tracker IDs (PR numbers, Linear keys) are human shorthand and sync linkage when a forge or tracker is present — never identity. CLI accepts unique slug fragments.
- Skill and guidance sweep: `shape` produces the role-named documents and teaches the task discipline; `implement` picks task files and checks boxes in the delivering commits; triage promotes intake items by seeding `brief.md`; vocabulary updated across templates, CLAUDE.md, and AGENTS.md.

**Out** (deferred, not rejected)

- `loaf change render` / `loaf web serve` / `loaf roadmap` — HTML and terminal projections of a change, the change set, or the release cohorts and their derived states (the gate computes the cohorts either way), per the served-not-committed doctrine; its own Intent.
- Committed `tasks.json` — revisit only if a sync adapter proves on-demand projection insufficient.
- Tracker sync adapters themselves (Linear/GitHub) — this unit builds repo mode; the mapping work is the SPEC-023 successor. Two mapping modes: change → project with tasks as issues (project-as-container trackers, Linear's native model), or change → tracking issue with tasks as sub-issues (project-as-product trackers); relations map natively either way, and Linear's native Releases map `target_release` directly. In tracker mode the tracker owns the planning surface — assigning and slipping targets, multiplayer — while the gate keeps reading git: evidence never delegates to an API.
- `docs/specs/` as a current-truth corpus — reflect-owned, created or amended after implementation proves what is true, deliberately conservative to avoid staleness.
- Converting historical `docs/changes/` units — the deprecation window exists so they never have to convert; the removal boundary decides their fate.
- Change-level dependency relations (`blocked-by` between changes) — cohort completion is a set test and git orders reality; add only if a real need emerges.

**Cut** (explicitly rejected)

- Renaming the unit — "Change" is the semantically unclaimed bucket word; every alternative carries a reserved meaning that collides with an inner document (`plan`, `spec`, `design`), a lifecycle stage (`brief`, `pitch`), or a register strain (`bet`).
- Local ID minting (`CHG-XXX` or any global counter) — no sound mint authority exists in a branch-native, offline-capable model; SQLite is machine-local, git-counting collides across branches, merge-time assignment arrives too late to be useful.
- Status-like fields anywhere — no `status` in `change.json`, no lifecycle in task frontmatter; completion and readiness are always derived.
- SQLite task entities or a mutable task lifecycle — task files are git-canonical; the retired task model stays retired. IDs return for parity; lifecycle does not.
- Forward pointers (`next`) — they force mutating committed nodes, which the immutability replay exists to forbid.
- Committed derived views (live-state renders, report indexes) — anything whose content derives from current state is served on demand, never committed, per the journal-render doctrine; authored reports with data baked in at writing time are ordinary committed artifacts in `reports/`.
- `implementation.md` — implementation lives in task files and PR diffs; prose narration of code is a staleness generator.

## Observable Workflow

Capture to change: triage promotes a spark, idea, or Intent by running `loaf change init <slug>` and seeding `brief.md` with the original ask; the Intent resolves by pointing at the change. When shaping happens live, the brief moment never existed and `shape.md` is written directly.

Shaping: `/shape` fills `shape.md` (and `plan.md`/`design.md` when the how needs prose), seeds the initial task decomposition in `tasks/`, and `loaf change check` reports violations and derived executability. Derived states fall out of artifacts: brief-only → captured; `shape.md` passing check → shaped; tasks provenance in HEAD → executing; checkboxes done or descoped → complete. Cohort members have one further state, the only one the gate reads: executable criteria met plus fresh receipt → verified (H-tier stays review material); untargeted changes end at complete and never need a receipt.

Executing: an implementer — or a subagent briefed with the task file itself — picks `tasks/TASK-002-scaffold.md` and lands it as an atomic commit that flips its checkboxes alongside the work: a task is a commit, not a PR. PRs batch task commits; under squash-merge the batch collapses to one commit whose diff still carries the flips, so the gate is merge-mode-agnostic, while per-task history survives on main only under merge or rebase modes — in-branch cleanup keeps branch history reading as the task list either way. A coordination task carries no production commit; its closing box rides any batch commit. Plan and work travel together, and that habit is what the gate reads as execution provenance. A discovered new problem becomes an Intent, never `TASK-007`.

Merging: the change PR is the change's whole life — draft as the shaping anchor, implementation commits flowing in, reflect distilling the Durable Outputs on the branch once verification passes — and it merges only when everything is done. On main, a healthy cohort member therefore only ever appears as verified; any lesser on-main state is the conduct violation the gate exists to catch. A shaped-but-unimplemented folder is a shaped intent and stays on its branch; the one sanctioned early merge is a captured promise carrier (brief + `change.json` with a target) hard-binding a release to future work — the 2.0.0 migration's own pattern.

Releasing: cutting `2.0.0` on a repo at `2.0.0-alpha.N` where a change declares `target_release: 2.0.0` but has no execution provenance, `loaf release --dry-run --bump release` (the finalization path — `--bump minor` from a prerelease would candidate `2.1.0`) reports `release blocked: change "<slug>" targets 2.0.0 but is not executed`. After its tasks land and `loaf change verify` writes a receipt matching the current criteria digest, the same command proceeds; a receipt verified at an older commit triggers a criteria re-run at preflight rather than a block. A legacy-layout cohort member is blocked with a convert-first message until the sanctioned conversion lands; a retarget to a later release is surfaced, never blocked. `--bump prerelease` flows in every state.

Referencing: "the work-model change" resolves by slug fragment; `change-work-model/003` is the stable external task reference, resolving to `tasks/TASK-003-*.md`; `loaf change show` prints the derived PR set; when Linear or GitHub is connected, their numbers serve as shorthand and the adapter owns the mapping.

Deprecation: `loaf change check` against an old single-file unit prints the familiar report plus one notice naming the new layout and the removal boundary.

## Rabbit Holes and No-Gos

- **`loaf change check` is not a workflow engine.** It validates structure and derives executability; no progress percentages, no burn-down state, no checkbox analytics.
- **The receipt stays cohort-only.** Extending receipts to every change is ceremony creep; the hash-binding pattern is proven but its scope is changes that declared a `target_release` — opting in is the trigger, and there is no other.
- **`brief.md` must not become a pseudo-shape.** It never satisfies anything mechanically; anyone writing the full problem and solution there is shaping with extra steps, and check's derived state says so.
- **Do not grow the roadmap into a planner.** Cohorts are derived sets; `target_release` is one mutable field. No milestone entities, no date fields, no priority ordering — trackers own planning; Loaf owns evidence.
- **Do not build the GUI or sync adapters "while we're here."** This unit ships the structure they consume, nothing more; task files never grow assignee, estimate, priority, or state fields toward tracker-parity-in-git.
- **The gate is accident-proofing, not tamper-proofing.** A repo owner can edit the gate's own source, so deliberate evasion — hand-authored receipts, criteria weakened to a trivial command — is out of threat model; it is what human review of a cohort member's `shape.md` diff exists to catch. Mechanical anti-forgery is rejected ceremony.

## Decisions

Provenance: interviews and debate 2026-07-25 through 2026-07-27 (journal: `discover(release-gate)`, `decision(sequencing)`, `finding(work-model)`, `decision(work-model)`), the NotebookLM corpus debate against Shape Up, Linear Method, SDD, and OpenSpec sources — including the semantic-collision verdict on "Plan" as a bucket name — the gate defect proven mechanically in an isolated worktree, and register-testing candidate names across feature, bugfix, and refactor work.

1. **Split-first sequencing.** The release-gate fix is defined inside this unit rather than built twice. Forecloses shipping the gate fix independently against the old frontmatter.
2. **Git provenance is the ship-proof; the receipt is cohort exactness.** Provenance (task-file commit + outside paths) proves work landed for any change; the committed receipt proves a cohort member's criteria were met. SQLite facts were rejected because the gate must hold on CI and other machines; slug-grep heuristics were rejected as trivially satisfiable.
3. **`target_release` defines the arc; no graph.** A change optionally declares the release it is bound for, and the cohort sharing a target *is* the arc — derived, never declared. No `arc`/`previous`/`terminal` fields, no chains, no freezes, no root/terminal validation: the gate hangs on the release itself instead of a designated proxy change. Mutable by design — a retarget is a visible, reviewable roadmap decision surfaced from history, the exit the graph model lacked. Cross-change sequencing stays out of the gate: cohort completion is a set test, and git orders reality. Supersedes both the lineage/release-after design and the arc/previous/terminal design.
4. **Change is the bucket — the unclaimed word is the qualification.** "Plan" as container creates semantic collision with its reserved agentic meaning (the technical blueprint): a Plan containing a `plan.md` makes "update the plan" unresolvable. The bucket must be the word with no reserved inner meaning, and "change" is it; the git-vocabulary overlap is honest (in a git-canonical model the folder describes the delta the PRs realize). Supersedes both the keep-Change-v1 and Plan-v2 decisions; third and final form.
5. **Narrative/state split.** Narrative documents settle at shaping; `tasks/` mutates during execution. The evidentiary boundary is which files change when, not which prose is which.
6. **Role-named narrative documents, accretive by need.** `shape.md` required (observable outcomes, boundaries, criteria — the corpus's spec sense); `plan.md`/`design.md` optional (internal engineering route); `brief.md` optional (the pre-shaping ask, archeological by design — the bootstrap BRIEF.md semantics at change scale). Names match reserved meanings, so pointing an agent at "the contract" or "the approach" is unambiguous.
7. **Tasks are identified files with derived completion.** `TASK-NNN-slug.md` numbered-record identity, tracker-native relations (`parent` for containment — declared on the child, children derived, backward pointers only — plus `blocks`/`blocked-by` for sequencing and `relates-to`; Linear's own set, so hierarchy syncs natively as sub-issues), subtask checkboxes checked in delivering commits. Each file is a self-sufficient delegation packet — a subagent's complete brief. IDs return for tracker parity; lifecycle does not — a checkbox flip is committed evidence bound to the delivering commit.
8. **Tasks are commits, not PRs.** A task is one atomic commit's worth of work — a pure coordination task carries no production commit, its closing box riding any batch commit — and PRs are integration batches of task commits. The gate is merge-mode-agnostic: a squash-merge collapses the batch into one commit whose diff still flips the boxes; per-task commits survive on main only under merge or rebase modes, which is why in-branch cleanup keeps branch history reading as the task list. The vertical discipline moves to decomposition and batching: partial execution must leave main coherent, so scope hammering cuts unstarted tasks cleanly.
9. **The task-vs-change boundary is the problem boundary.** Same problem, another task; different problem discovered mid-work, an Intent and its own change. This is the rule `journal-reliability-foundation` broke.
10. **Retargeting is the exit; prerelease is the valve.** Slipping a change to a later release is a legitimate roadmap decision made in a reviewable diff — surfaced by the history replay, never blocked (accident-not-tamper). An unfinished cohort blocking its own version is the incentive working; it no longer holds every other release hostage.
11. **Derived views are served; authored reports are committed.** Anything rendering live state — task completion, gate status, report indexes — is an on-demand CLI projection (`loaf change tasks --json` now; `loaf change render`/`loaf web serve` later), because a committed copy drifts into a lie. Authored documents with data baked in at writing time (reviews, visuals, audits) are ordinary artifacts committed under `reports/`, so a PR reviewer opens the change's visual model from the branch.
12. **Identity is the slug; numbers are borrowed, never minted.** Global slug uniqueness is already enforced; `slug/NNN` is the external task reference, resolving to the `tasks/TASK-NNN-*.md` file; tracker IDs (PR numbers, Linear keys) are shorthand and linkage when present — the PR set is derived from squash subjects, not stored. Forecloses `CHG-XXX` and any global counter; `TASK-NNN` stays local to its owning change, so no mint authority is needed.
13. **The receipt is a cache of verify, not a credential.** It records the criteria digest and the commit it verified; preflight re-runs the declared criteria when any later commit touches a path other than the receipt file itself — the receipt's own commit never stales it (the bootstrap case round 2 caught), and a criteria-only digest would have survived a revert of the verified work. Binding to `shape.md`'s criteria keeps approach churn free. Receipts are new-layout-only: a legacy cohort member converts before it can verify, because digesting prose does not make it executable. Supersedes the plan.md binding, the digest-only design, and round 1's legacy-digest patch.
14. **Executable criteria declare their commands.** An executable V-entry carries its command and expected result; `loaf change verify` runs exactly the declared commands and records command, exit, and output digest in the receipt — nothing inferred from prose. Human-judgment criteria stay prose in the H-tier and are review material — enforced by ship's review and the approval report, never by the release gate. Syntax is TASK-005's tactical choice against the capability-receipt precedent.
15. **Criteria gate; tasks are the route.** Cohort-member doneness is the contract proven at HEAD, never checkbox count — an unchecked task on a verified change is descoped work, cut cleanly. Gating on checkboxes would train false assertions and break scope hammering. `--require-executable` therefore demands provenance, not full completion.
16. **Ceremony reports are namespaced by kind, from a closed registry.** `reports/` files are `YYYYMMDD-HHMMSS-<kind>-<slug>.html`; the registry ships in the binary with a skeleton variant and guidance section per kind — `approval` and `review` reserved so a future publish ceremony can wire them in (nothing in *this* change is load-bearing on them; the ceremony is its own Intent), `visual`/`audit` informational, `note` the escape hatch whose recurring topics signal when a new kind has earned registration. Unknown kinds are refused; extending the registry is a normal change.
17. **The change PR is the change's whole life; main carries only completed changes.** Shaped-but-unimplemented is a shaped intent living on its branch. Implementation, verification, and reflect-distilled Durable Outputs ride the same PR, which merges only when everything is done — reflect stays post-implementation (never during shaping, preserving the anti-staleness rule) but moves pre-merge. The gate enforces this conduct for cohort members: any on-main state below verified is the accident it catches. The sole sanctioned early merge is the captured promise carrier; per-task PRs remain the exception for genuinely multi-integration changes.

## Planning Contract

### Approach

The anatomy lands as a new scaffold plus a layout-agnostic loader, not a migration. The loader assembles the same in-memory node from either layout in the same root — `change.json` presence selects the new anatomy, bare `change.md` selects legacy — so cohort derivation, retarget history, and the retention guard stay single-sourced. The gate and receipt build on the loader's layout-agnostic view: provenance keys on the layout's execution surface (`tasks/` new, `change.md` old), so the gate closes for both layouts the day it ships.

### Placement

CLI work stays in `internal/cli`: the loader beside `change_lineage.go`, provenance with the gate, `verify`/`tasks` verbs in the existing `change` command family, scaffold templates beside the existing change template. Skill updates live in `content/skills/shape`, `content/skills/implement`, and `content/skills/triage`; guidance in `.agents/AGENTS.md` and `.claude/CLAUDE.md` follows shipped behavior, never ahead of it.

### Metadata history across surfaces

Nothing in `change.json` freezes: identity fields must match the folder (validated as today), and `target_release` is mutable — the replay **unions both surfaces' histories** per unit to derive retarget events (`2.0.0 → 2.1.0 at <commit>`, including removal-to-none), which `check`, `show`, and the release preflight surface and the gate never blocks on; the current value alone gates. This **replaces**, not extends, the current machinery: path-keyed deletion detection and immutable-field replay give way to unit-keyed (slug + folder identity) retention and mutable-event replay across both surfaces, with atomic conversion recognized as replacement rather than deletion. The retention guard blocks deleting or renaming away any unit whose history ever declared a `target_release` (or legacy `lineage`/`release-after`). Sanctioned layout conversion is an atomic same-commit replace — `change.json` with values carried verbatim lands in the commit that retires `change.md`, **all task checkboxes unchecked at conversion** (pre-checked boxes are a violation: flip-grade execution must come from later delivering commits, never be manufactured by conversion) — and keep-both remains transitional-legal with the current target read from the union. The live promise migrates by carrier materialization, never bare translation: the sweep unit does not exist in main today (`release-after` on `journal-reliability-foundation` points at an unmaterialized slug), so TASK-004 materializes the carrier — the sweep or its re-shaped successor declaring `target_release: 2.0.0` — in the same change that retires the freeze replay, so the promise is never unheld.

### Provenance precision

Two grades, both requiring the companion path outside `docs/changes/` entirely so cross-change task edits never count. The path-level rule feeds derived display states for every change: executed means a commit modifies `tasks/` plus such an outside path; scaffold commits are folder-local and can never read as execution. The gate path — changes declaring a `target_release`, the only place a release hangs on the answer — uses content-level detection from the start: only `- [ ]`→`- [x]` transitions outside code fences count, parsed at preflight over each cohort folder; reverse flips, added unchecked boxes, and whitespace or title edits are non-events, each with a negative fixture. Mixed commits and non-semantic task-file touches therefore cannot open the gate, and the receipt remains the lock either way.

### Compatibility and the removal boundary

Both layouts are first-class inputs to every reader until a named removal boundary (candidate: the first stable release after the new layout has shipped one minor — one formulation everywhere), recorded in the deprecation notice itself. Nothing rewrites an old unit in place, and legacy units' display states derive through the `change.md`-keyed path grade, their residual shaping-edit ambiguity accepted as strictly narrower than the presence-only defect being closed. The exception with teeth: a **cohort member cannot satisfy the gate from the legacy layout** — prose criteria cannot be executed and the file has no checkboxes to flip — so the live promise's carrier `spec-conversion-and-guidance-sweep` declares `target_release: 2.0.0` (legal in legacy frontmatter) and converts via the sanctioned atomic replace as part of its own execution, which its rework makes natural. Until it converts and verifies, 2.0.0 stays blocked with a convert-first message; prerelease flows regardless.

### Risks

- The provenance convention requires execution to touch task files. The scaffold makes it structural (checkboxes live in `tasks/`), the implement skill instructs it, and the failure direction is safe: work that never touched its task file reads as unexecuted and blocks stable until a one-commit remedy, never a wrongly opened gate.
- Receipt expiry via criteria-digest drift is a known canary pattern that fired four times during capability work; `loaf change verify` must report a digest mismatch plainly so re-verification is mechanical.
- Renaming a remote branch under an open PR closes the PR rather than retargeting it (learned on PR #139, confirmed on PR #140); a mid-shaping rename means superseding — or, when the original branch name returns, reopening the original PR, which is how #139 came back.

### Sequencing

TASK-001 and TASK-002 are ordered (schema before scaffold); TASK-003 depends on both; TASK-004 and TASK-005 depend on TASK-003, and TASK-004 ships the gate provenance-only — the receipt requirement and stale-receipt re-run activate when TASK-005 lands; TASK-006 follows shipped behavior. Each task leaves main coherent: layout without gate keeps today's gate behavior; gate without receipt enforces provenance alone.

## Implementation Units

- **TASK-001 — `change.json` schema and layout-agnostic loader.** Parse the new surface (identity + `target_release` in the canonical `MAJOR.MINOR.PATCH` literal — no `v`, leading zeros, prerelease, or build suffix — closed schema), derive cohorts, detect layout by `change.json` presence with legacy fallback in the same root (malformed `change.json` fails closed as a violation, never a silent fallback), replace the single-content node with parsed metadata plus per-layout contract evaluation, and migrate every `change.md`-resolving consumer — init duplicate detection, folder and branch resolution, list/check, and the committed-HEAD loader. - **TASK-006 — Skills and guidance sweep.** `shape` produces the role-named documents and teaches the problem-boundary and vertical-slice tests; `implement` picks task files and checks boxes in delivering commits; `triage` promotes intake by seeding briefs; vocabulary swept across templates and guidance.
