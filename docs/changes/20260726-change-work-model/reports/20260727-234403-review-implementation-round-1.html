Implementation Review — Round 1

reviewed 2026-07-27 · six commits 3f381d01…125ef6ea read against shape.md · verdict REQUEST-CHANGES · 3 blockers + 6 major + 4 minor · dispositions decided 2026-07-28, handed off as TASK-007…TASK-014

The headline defect is closed. --bump release and --post-merge both exit 1 on the unexecuted 2.0.0 carrier; --bump prerelease flows; --bump minor proceeds with the lower-cohort warning. The candidate-first restructure, the dual-layout loader, the closed schemas, the projections, and the report registry all behave as shaped.

But the lock does not lock. A receipt written by a failing loaf change verify satisfies the gate — proven end-to-end in a fixture that cut a stable 1.0.0 with a receipt recording exit_code: 1, ok: false. Combined with a criteria syntax that the shipped template gets wrong, the verification tier is currently decorative: no change shaped from the scaffold can produce parseable criteria, and any change that manages to can pass the gate on failed ones.

Decisions taken on this round

Four findings were design calls rather than defects. All four are now decided, and the task packets are written against these answers.

  • M2 — build the ladder, do not retreat the doc. verified is the predicate the gate reads, and a model whose gate has no name in any projection is unfinished; round 3's finding 1.3 already accepted the ladder as the fix for untargeted changes lacking a done state. Both missing states are nearly free once B1 lands. Keep executable and amend shape.md to name it. → TASK-011
  • M4 — tighten the detector, do not restate the grammar. The looseness is reachable by ordinary editing: rewording a step reads as execution today. Require same-hunk, same-label pairing. A commit that flips and rewords at once stops counting, which is a false negative — the direction shape.md's Risks section already declares safe. → TASK-009
  • m1 — criteria run from the repository root. Every realistic criterion is repo-scoped, and the current default produces silent false passes (go test ./... in a docs subdirectory matches no packages and exits 0). A criterion that proves nothing while reporting green is the one failure direction a gate cannot tolerate. Record the cwd in the receipt. → TASK-008
  • m3 — seed a real task packet. The design leans entirely on the delegation-packet format and nothing puts it in front of a shaper. Seed TASK-001-first-slice.md with unchecked boxes; it cannot manufacture provenance, and V3 must stay green. → TASK-013

m4 is recorded as a note with no task: the dogfood wrinkle self-healed and needs no code.

Blockers

B1blockerA receipt from a failed verification opens the stable gatefix before merge

Evidence

changeReceiptStatus (internal/cli/change_verify.go:230) validates three things — receipt exists, criteria digest matches, receipt is fresh — and never reads receipt.Results[].OK. runChangeVerify writes the receipt at line 128 before returning ExitError{Code: 1} at line 135, so a failing run still leaves a committed artifact.

fixture at 1.0.0-alpha.1, member declares target_release: 1.0.0
$ loaf change verify …          fail V1  test -f README.md
                                Wrote receipt: …/receipts/verify.json
$ git commit -m "chore: record failing receipt"
$ loaf release --dry-run --bump release
                                New version: 1.0.0        ← gate opened
$ grep ok …/receipts/verify.json
                                "exit_code": 1,  "ok": false

Why it matters

This is the accident path, not the tamper path the threat model excludes: run verify, see it fail, commit the branch, open the PR. Scope says a cohort member must be "executed at the flip grade, and receipt-verified" — the receipt currently attests that verification ran, not that it passed.

Suggested shape of the fix

Gate on every Results[].OK being true (reason: "receipt records failing criteria"), and consider refusing to write a receipt at all on failure — or writing it with an explicit failure marker the gate keys on. Add the negative fixture; its absence is why this slipped.

B2blockerThe shipped criteria syntax never parsesfix before merge

Evidence

The scaffold's shape template writes the command inline on the V-entry line — - [**V1.** What must be true. Command: `exact command`. Expect: …] — but changeCriterionCommandRE (change_verify.go:21) is anchored ^\s*-\s*Command:, so it cannot match a line beginning - **V1.**. The parser's own comment at line 168 says "Inline Command: `…` on the same header line", so the intent was inline support; the regex forbids it. Only a sub-bullet form works, and that form appears nowhere except one test fixture.

Why it matters

Every change shaped from the shipped scaffold has zero executable criteria, so loaf change verify refuses with "no executable criteria found", so a cohort member can never satisfy the gate. This change's own V1–V9 are among the casualties — loaf change verify docs/changes/20260726-change-work-model refuses today, which is legal (no target_release) but means the verify path has only ever run against fixtures.

Suggested shape of the fix

Make the regex unanchored for the header-line case (or accept both forms explicitly), then assert both forms in tests, and teach the working form somewhere a shaper will find it — the shape skill or cli-boundary.md, neither of which mentions Command: at all.

B3blockerV7 is red: go test ./... fails on the stale installed-smoke receiptfix before merge

Evidence

57 subtests across 10 parent tests fail, all one root cause: the three capability receipts under docs/changes/20260710-journal-reliability-foundation/research/ pin native binary SHA-256 40afe75f… (main's binary) while this branch's rebuilt binary is 8f4f98a8…. Every failure message is the same hash mismatch.

Why it matters

The Definition of Done requires V1–V9 green in CI. This is the known canary shape.md's own Risks section names ("fired four times during capability work"), and the remedy is mechanical — re-record the receipts against the rebuilt binary, as the version-agnostic-managed-block change did. It is bookkeeping, not architecture, but it is currently a red suite.

Major

M1majorTwo surfaces disagree about the same change's derived statefix before merge

Evidence

loaf change list reports state=executed for change-work-model; loaf change show reports state: executable for the same folder. runChangeShow (change_tasks.go:210) derives state from captured / shaped / executable only and never calls changeFolderExecuted. Worse, show --json carries no state field at all — the string is computed inside the print path, so a JSON consumer cannot see it.

Why it matters

Derived state is the whole premise ("completion and readiness are always derived"). Two derivations that disagree make the projection untrustworthy exactly where an agent or adapter would read it.

M2majorThe state ladder accepted at round 3 was not implemented — complete and verified do not existfix before merge

Evidence

Observable Workflow declares captured → shaped → executing → complete, plus verified for cohort members (the ladder split accepted as r3 finding 1.3). The code emits captured, shaped, executable, executing, executed — grep '"verified"\|"complete"' across internal/cli/change*.go returns nothing.

Why it matters

A verified cohort member is indistinguishable from an unverified one in every projection, so the state the gate actually reads is the one state no surface can display. Either the code adopts the shaped vocabulary or shape.md is corrected to the shipped one — but they cannot both stand, and the doc is the contract.

M3majorThe code-fence exclusion in flip detection is not implementedfix before merge

Evidence

diffContainsCheckboxFlip (change_provenance.go:108) skips lines that are fence markers but never tracks fence state — its own comment concedes "stripping fenced regions is hard". A checkbox flipped inside a fenced block therefore counts as execution provenance.

Why it matters

Provenance precision requires "only - [ ]→- [x] transitions outside code fences", and V1 claims a negative fixture for each non-event. There is no fenced-checkbox fixture in the suite. A task file documenting checkbox syntax in a fenced example would open the gate.

M4majorFlip detection pairs any removed unchecked box with any added checked boxdecide

Evidence

The function accumulates hasAdd and hasRemove independently over a file's whole patch and returns their conjunction. The two need not be the same checkbox or the same hunk: deleting an unchecked step (descoping) while adding a pre-checked step elsewhere in the file registers as a flip with no transition anywhere.

Why it matters

Acceptable as the coarse filter if the receipt is the lock — which B1 shows it currently is not. Worth deciding explicitly: tighten to hunk-local pairing, or restate the grammar as "removed unchecked + added checked in the same file" and fixture it honestly.

M5majorThe pre-checked-conversion violation (r3 finding 2.5) was never builtfix before merge

Evidence

The Planning Contract requires "all task checkboxes unchecked at conversion (pre-checked boxes are a violation)" and V4 asserts it. No code references the rule and no test covers it — grep -i 'pre-checked\|unchecked at conversion' over internal/cli returns nothing but the retention test's atomic-conversion case, which says nothing about boxes.

Why it matters

This is precisely the manufactured-execution hole Codex found at round 3 and the shape accepted closing. A conversion carrying checked boxes plus one outside path currently reads as flip-executed.

M6majorCoverage is thinnest exactly where the gate is load-bearingfix before merge

Evidence

change_verify_test.go is 39 lines and two tests: writes-a-receipt, legacy-refused. Absent: digest-expiry after a criteria edit, plan.md immunity, freshness re-run past the verified commit, receipt's-own-commit exemption, retarget-after-verify — all five named in V5. The gate suite has four tests; absent: prerelease bypass in every gate state (V2), --post-merge finalization, path-grade-is-not-flip-grade, a second shaped-only member, no-target-never-gates, and the reverse-flip / added-unchecked / whitespace negatives (V1).

Why it matters

V1, V2 and V5 read as verified but are partially covered, and B1 lives squarely in the untested region. The regression the whole change exists to prevent needs its fixtures before merge, not after.

m4minorDogfood wrinkle: TASK-001's boxes were born checked, then re-checked inside the TASK-004 commitnote only

Evidence
