Post-merge serves two flows — the code now knows only one

authored 2026-07-28 · explains finding O6-2 on board 20260728-143458 · code state at 64810d87

The two flows

Flow A — publish a prepared prerelease the routine one
Release commit prepares an alpha
package.json → 2.0.0-alpha.15, CHANGELOG → ## [2.0.0-alpha.15]
PR squash-merges to main
loaf release --post-merge
tags v2.0.0-alpha.15, publishes the GitHub prerelease

This is how alpha.12, alpha.13, and alpha.14 shipped. The prerelease valve exists for exactly this flow — prereleases never gate.

Flow B — finalize stable the rare, gated one
Release commit prepares stable
package.json → 2.0.0, CHANGELOG → ## [2.0.0]
PR squash-merges to main
loaf release --post-merge must gate
the 2.0.0 cohort (every change with target_release: 2.0.0) must be executed + receipt-verified
Then tag v2.0.0

Round 3 correctly closed the bypass where Flow B could tag stable without the gate. The mistake was writing the fix as if every post-merge were Flow B.

What the code does today — Flow A, broken at three points

Version files at HEAD say 2.0.0-alpha.15
the version the release commit actually prepared
① resolveReleaseSnapshot strips the prerelease
change_release_gate.go:237-245 — "Finalization targets the stable form" → Candidate = 2.0.0. The prepared version is discarded here and never used again.
② The 2.0.0 cohort gate fires on an alpha publish
the sweep carrier is open by design → the alpha train halts until the whole 2.0.0 cohort is verified — the valve closed on the flow it exists for
③ Even past the gate, the guardrails check the wrong version
changelog guardrail demands ## [2.0.0] (files carry ## [2.0.0-alpha.15]) → abort blaming the changelog; tag collision and the tag itself use 2.0.0
The converse hazard

If a stray ## [2.0.0] section did exist, post-merge would tag and publish v2.0.0 while every version file still says 2.0.0-alpha.15 — and the old guardrail 4, which used to assert tag = version files, was reduced to a cross-file consistency probe that discards the version (release_post_merge.go:112). Nothing relates the tag to the files any more.

How it got in — a three-link chain
shape.md V2: "post-merge finalization is blocked until the cohort completes" conflates A and B → TASK-024 packet: "the tagged version is the preflighted candidate" the Warden's sentence → lane implements the sentence faithfully not the lane's error

The contract encoded Flow B as the only flow; the packet repeated it; the implementation obeyed. Tests pass because the fixtures were written from the same sentence.

The proposed fix — key on the prepared version

Version files at HEAD sayMeaningGateTag
2.0.0-alpha.15 (prerelease) Flow A — publishing a prepared prerelease valve open — no stable gate, exactly as --bump prerelease v2.0.0-alpha.15 — the prepared version
2.0.0 (stable) Flow B — finalizing stable cohort gated — every target_release: 2.0.0 member executed + verified v2.0.0 — the prepared version

Guardrail 4 restored: the tag always equals the consistent version-file version — the one invariant that holds in both rows. Round 3's bypass stays closed: preparing stable files can never tag without the cohort, because stable-prepared is the gated row. One clause of V2 amends from "post-merge finalization is blocked until the cohort completes" to "post-merge gates the cohort when the prepared version is stable; a prepared prerelease publishes through the valve."
