C3-1blockerOmitted --bump gates one version while the executor cuts anotherconfirmedfix before merge

Codex claim

change_release_gate.go:201 / release_dry_run.go:443 — preflight's candidate defaults to the current version when --bump is omitted, but the executor then derives the real bump from suggestReleaseBump(commits), so the gate checks the wrong cohort.

Warden verification

Confirmed by code read: computeReleaseCandidateVersion returns current on empty bump (both branches of its conditional — the prerelease guard is dead code), while runReleaseDryRun computes bump := suggestReleaseBump(commits) independently. Current 1.0.0, incomplete target_release: 1.1.0 cohort, one feat commit: preflight gates 1.0.0's cohort, release cuts 1.1.0 ungated. The default invocation is the bypass.

Fix shape

One candidate computation, shared: derive the effective bump (flag or suggestion) first, hand the same resolved candidate to both the gate and the executor. Fixture: no-flag invocation blocks on the suggested version's incomplete cohort.

C3-2blocker"Structurally valid" is enforced as "no violations" — executability and task findings never gateconfirmedfix before merge

Codex claim

change_release_gate.go:59 — the cohort loop checks only report.Violations; structural gaps, task-hygiene findings, and conversion findings are invisible to the gate.

Warden verification

Confirmed: the loop reads len(report.Violations) alone. report.Executable is never consulted, and task findings are produced by loadChangeTasks outside evaluateChangeNode entirely. A member with an empty Planning Contract, or banned task frontmatter, that still carries flips and a passing receipt releases — while loaf change check on the same folder fails. The contract term "structurally valid" (Scope) is broken.

Fix shape

The gate's structural test becomes the same composite check drives: violations + task findings + conversion findings block; executability gaps block cohort members (a contract with empty sections is not a contract the receipt can attest). Fixtures for each tier.

C3-3majorReceipt is read from the working tree, not committed HEADconfirmedfix before merge

Codex claim

change_verify.go:256 — preflight loads receipts/verify.json via the filesystem, so an uncommitted receipt with verified_commit == HEAD reads as fresh, contradicting ADR-023's committed-evidence guarantee.

Warden verification

Confirmed: loadChangeVerifyReceipt(folderAbs) is an os.ReadFile. Run verify at HEAD, don't commit, run release --dry-run: the cohort reports verified on evidence that exists on one machine only. ADR-023 states "evidence is always committed before it is read" — the code contradicts its own ADR the day it shipped.

Fix shape

Read the receipt from HEAD (git show HEAD:<path>) in gate context; keep filesystem reads for verify's own output. Fixture: uncommitted receipt blocks with a commit-the-receipt remedy.

C3-4majorFence tracking sees only the ±3-line patch, so distant fences are invisibleconfirmedfix before merge

Codex claim

change_provenance.go:95 — fence state is inferred from a --unified=3 patch; a checkbox inside a fenced block whose opening fence sits more than three unchanged lines above still scores as execution.

Warden verification

Confirmed — the code's own comment states the broken assumption: "unified=3 keeps nearby fence markers as context so fence state is trackable." Nearby is not guaranteed. The round-2 fixture kept its fence within context, which is why it passed.

Fix shape

Fence state must come from the full post-image file (git show commit:path), mapping flip lines to file positions — or a large --unified window with a full-file fallback. Fixture: fence opened ten lines above the flip.

C3-5majorExpect: is parsed, documented, digested — and never enforcedconfirmedfix before merge

Codex claim

change_verify.go:94 + the shape template — success is exclusively exit-code zero, so "Expect: specific output" is decorative; a command exiting 0 with wrong output gets ok: true and its receipt opens the gate.

Warden verification

Confirmed: ok := runErr == nil && exitCode == 0; Expect feeds only the criteria digest. The template's own example teaches "Expect: exit 0 and/or specific output" — an author who writes an output expectation believes it is being checked. It is not.

Fix shape

Either enforce a defined Expect grammar (exit code + optional output-contains), or narrow the template and docs to what is enforced. Enforcing is the honest direction — the receipt already records the output digest. Grammar decision is the owner's; fixtures both directions.

Packets committed unchecked before execution, per the discipline this branch taught.
