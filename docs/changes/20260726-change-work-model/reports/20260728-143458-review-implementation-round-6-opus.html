O6-2majorPost-merge now tags the stable candidate instead of the prepared version — breaking prerelease publishingconfirmedfix + shape amendment — owner decides

Verification

resolveReleaseSnapshot (change_release_gate.go:237-245) sets the post-merge candidate to stable-of-current; release_post_merge.go uses snapshot.Candidate for the changelog guardrail (:120), tag collision (:125), and the tagged version (:140), and guardrail 4 was reduced to a cross-file consistency probe that discards the version. The alpha train — this repo's own alpha.12→14 flow — would abort on a missing ## [2.0.0] changelog section; the converse case would tag a version no file carries.

Provenance of the defect — two layers

The TASK-024 packet wrote "the tagged version is the preflighted candidate or the run aborts"; the lane implemented that sentence faithfully. Behind it, shape.md's V2 clause ("the same fixture's --post-merge finalization is blocked until the cohort completes") conflates two flows post-merge actually serves: publishing a prepared prerelease (must tag the prepared version and flow through the prerelease valve) and finalizing stable (must gate the stable cohort). Under the current code the next alpha release blocks on the 2.0.0 cohort — the valve closed on the flow it exists for.

Proposed resolution

Post-merge keys on the prepared version (the consistent version-file version at HEAD): prerelease prepared → prerelease publish — tag it, no stable gate; stable prepared → stable finalization — gate that version's cohort, then tag it. Guardrail 4 restored to relate the tag to the version files. One clause of V2 amended to say exactly that; round 3's bypass stays closed (preparing stable files can never tag without the cohort). Shape amendment = owner approval.
